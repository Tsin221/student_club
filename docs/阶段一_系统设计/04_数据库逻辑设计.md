- **编写与验收依据**：`00_阶段一任务指引_供新智能体.md`。

- **状态依据**：`02_业务状态与状态流转.md`。

## 1. 设计边界与命名

### 1.1 表范围

本文件只设计以下 13 张业务表：

1. `user`
2. `club`
3. `club_membership`
4. `recruitment`
5. `join_application`
6. `announcement`
7. `post`
8. `reply`
9. `post_like`
10. `notification`
11. `club_evaluation`
12. `feedback`
13. `content_report`

不建立社团分类表、平台角色表、负责人表、通知阅读表、附件表、图片表、审计表、状态历史表、AI 记录表或统计结果表。

### 1.2 命名与类型约定

- 表名和字段名使用英文蛇形命名。
- 除纯关系表 `post_like` 外，各实体表使用 `id` 作为技术主键，建议类型为 `BIGINT UNSIGNED`，由系统自动递增生成；`post_like` 直接使用 `(user_id, post_id)` 联合主键，避免增加无必要字段。
- 所有外键与目标 `id` 使用相同类型。
- 业务时间统一使用 `DATETIME`；文档不额外增加时区、更新时间或状态变更时间字段。
- 布尔值使用 `TINYINT(1)`，只允许 `0` 和 `1`。
- 固定业务取值使用 MySQL `ENUM` 建议类型；这些枚举直接对应已通过需求中的中文值，不建立字典表。
- `TEXT` 是存储类型，产品输入上限另按已确认规则校验：帖子正文最多 5000 字，回复内容最多 1000 字。
- 除主键外，文档中的“无默认值”表示创建记录时必须由用户输入、业务上下文或服务端生成后明确写入。

### 1.3 不重复存储原则

- 社团负责人名单及联系方式从 `club_membership` 与 `user` 查询，不写入 `club`。
- 回复所属社团从 `reply.post_id -> post.club_id` 查询，不写入 `reply`。
- 举报所属社团从目标帖子或目标回复查询，不写入 `content_report`。
- 招新“未开始、进行中、已满、已结束”动态计算，不写入 `recruitment` 状态字段。
- 入社申请只保存姓名和专业班级快照，不保存手机号快照。
- 通知不关联触发者、申请、举报、帖子、回复或其他通用业务对象。

## 2. `user` 用户表

### 2.1 表职责

保存登录凭据的安全存储结果、平台角色、账号状态、注册时间以及需求规定的学生资料。社团身份不保存在本表。

|---|---|---|---:|---|---|---|---|---|---|---|
| `id` | 用户 ID | `BIGINT UNSIGNED` | 否 | 自动递增 | 主键 | 主键唯一 | 主键索引 | 不适用 | 系统生成 | 历史业务引用存在时不得物理删除 |
| `username` | 用户名 | `VARCHAR(150)` | 否 | 无 | 否 | 单字段唯一 | 唯一索引 | 不适用 | 用户输入 | 登录唯一标识；需求明确要求全局唯一 |
| `password_hash` | 密码安全存储结果 | `VARCHAR(255)` | 否 | 无 | 否 | 否 | 无 | 不适用 | 系统根据用户密码生成 | 只保存安全哈希结果，不保存明文密码 |
| `platform_role` | 平台角色 | `ENUM` | 否 | `学生用户` | 否 | 否 | 与账号状态组成联合索引 | `系统管理员`、`学生用户` | 系统确定 | 社团负责人身份不得写入此字段 |

### 2.3 表级约束

- `username` 全局唯一。
- 建议建立 `(platform_role, account_status)` 联合索引，用于管理员筛选学生账号以及创建社团时查找账号正常的学生。
- 停用学生前必须在同一业务操作中检查其负责的全部正常社团，不能使任何正常社团失去最后一名有效负责人。

- 注销只更新 `status`，不级联修改或物理删除任何历史业务记录。

## 4. `club_membership` 社团成员关系表

### 4.1 表职责

连接学生与社团，保存唯一成员关系的当前成员状态和社团身份。成员重新加入时更新原记录。

### 4.2 数据字典

| 字段名 | 中文含义 | 数据类型 | 是否允许为空 | 默认值 | 主键/外键 | 唯一约束 | 索引建议 | 枚举范围 | 数据来源 | 备注 |
|---|---|---|---:|---|---|---|---|---|---|---|
| `id` | 成员关系 ID | `BIGINT UNSIGNED` | 否 | 自动递增 | 主键 | 主键唯一 | 主键索引 | 不适用 | 系统生成 | 退出、移除或重新加入时均保留同一记录 |
| `user_id` | 成员用户 | `BIGINT UNSIGNED` | 否 | 无 | 外键 → `user.id`，删除限制 | 与 `club_id` 联合唯一 | 联合唯一索引前缀；另建议与状态组成查询索引 | 不适用 | 业务上下文 | 关联用户必须为学生用户 |
| `club_id` | 所属社团 | `BIGINT UNSIGNED` | 否 | 无 | 外键 → `club.id`，删除限制 | 与 `user_id` 联合唯一 | `(club_id, member_status, club_role)` 联合索引 | 不适用 | 业务上下文 | 用于成员列表、负责人列表和内部统计 |
| `member_status` | 成员状态 | `ENUM` | 否 | `在社` | 否 | 否 | 见 `club_id` 联合索引 | `在社`、`已退出`、`已移除` | 系统设置 | 不保存退出、移除或恢复时间及原因 |
| `club_role` | 社团身份 | `ENUM` | 否 | `普通成员` | 否 | 否 | 见 `club_id` 联合索引 | `负责人`、`普通成员` | 系统设置 | 初始负责人创建时明确写入 `负责人` |

### 4.3 表级约束

- `(user_id, club_id)` 联合唯一，确保同一学生与同一社团只保留一条成员关系。
- 建议建立 `(club_id, member_status, club_role)` 联合索引，支持在社成员、普通成员、有效负责人筛选和负责人统计。
- 建议建立 `(user_id, member_status)` 联合索引，支持“我的社团”和当前加入社团数量查询。
- 正常社团必须至少保留一名“账号正常、成员在社、身份为负责人”的成员；该约束需要服务端事务、行锁和联合查询保证，不能只依赖单行约束。
- 创建社团后的新增负责人只能从该社团当前在社、账号正常的普通成员中选择。
- 取消负责人身份只把 `club_role` 改为 `普通成员`；主动退出或被移除后重新加入时，恢复本记录为“在社、普通成员”。

## 5. `recruitment` 招新信息表

### 5.1 表职责

保存一次招新的文本内容、人数、有效时间、归属、发布信息及提前结束事实。展示状态不落库。

### 5.2 数据字典

| 字段名 | 中文含义 | 数据类型 | 是否允许为空 | 默认值 | 主键/外键 | 唯一约束 | 索引建议 | 枚举范围 | 数据来源 | 备注 |
|---|---|---|---:|---|---|---|---|---|---|---|
| `id` | 招新信息 ID | `BIGINT UNSIGNED` | 否 | 自动递增 | 主键 | 主键唯一 | 主键索引 | 不适用 | 系统生成 | 招新结束后保留历史 |
| `title` | 招新标题 | `VARCHAR(200)` | 否 | 无 | 否 | 否 | 无 | 不适用 | 对应负责人输入 | 纯文本 |
| `introduction` | 招新简介 | `TEXT` | 否 | 无 | 否 | 否 | 无 | 不适用 | 对应负责人输入 | 纯文本 |
| `requirements` | 招新要求 | `TEXT` | 否 | 无 | 否 | 否 | 无 | 不适用 | 对应负责人输入 | 纯文本 |
| `capacity` | 招新人数 | `INT UNSIGNED` | 否 | 无 | 否 | 否 | 无 | 正整数 | 对应负责人输入 | 调整后不得小于当前已通过申请数 |
| `start_time` | 开始时间 | `DATETIME` | 否 | 无 | 否 | 否 | 与社团、结束事实和结束时间组成联合索引 | 不适用 | 对应负责人输入 | 必须早于 `end_time` |
| `end_time` | 结束时间 | `DATETIME` | 否 | 无 | 否 | 否 | 见联合索引 | 不适用 | 对应负责人输入 | 超过此时间后动态状态为已结束 |
| `club_id` | 发布社团 | `BIGINT UNSIGNED` | 否 | 无 | 外键 → `club.id`，删除限制 | 否 | `(club_id, ended_early, start_time, end_time)` 联合索引 | 不适用 | 当前社团上下文 | 生命周期内不得改变归属 |
| `publisher_id` | 发布人 | `BIGINT UNSIGNED` | 否 | 无 | 外键 → `user.id`，删除限制 | 否 | 普通索引 | 不适用 | 当前登录用户 | 发布时必须是对应正常社团的有效负责人 |
| `published_at` | 发布时间 | `DATETIME` | 否 | 无 | 否 | 否 | 无 | 不适用 | 系统生成 | 不增加更新时间 |
| `ended_early` | 是否已提前结束 | `TINYINT(1)` | 否 | `0` | 否 | 否 | 见 `club_id` 联合索引 | `0`、`1` | 系统设置 | 只保存提前结束事实，不保存操作人、时间或原因 |

### 5.3 表级约束与动态状态

- `capacity > 0`，且 `start_time < end_time`。
- `ended_early` 只能从 `0` 变为 `1`，不提供恢复或重新开启。
- 动态展示状态按固定顺序计算：
  1. `ended_early = 1`，或服务端当前时间超过 `end_time`：已结束；
  2. 当前招新下 `join_application.status = 已通过` 的数量大于或等于 `capacity`：已满；
  3. 服务端当前时间早于 `start_time`：未开始；
  4. 其他：进行中。
- 不建立 `status`、已通过人数缓存、状态变更时间、结束人、结束时间或结束原因字段。

## 6. `join_application` 入社申请表

### 6.1 表职责

保存学生针对一次招新的申请、提交时姓名与专业班级快照以及申请状态。申请状态本身就是审核结果。

### 6.2 数据字典

| 字段名 | 中文含义 | 数据类型 | 是否允许为空 | 默认值 | 主键/外键 | 唯一约束 | 索引建议 | 枚举范围 | 数据来源 | 备注 |
|---|---|---|---:|---|---|---|---|---|---|---|
| `id` | 入社申请 ID | `BIGINT UNSIGNED` | 否 | 自动递增 | 主键 | 主键唯一 | 主键索引 | 不适用 | 系统生成 | 审核后继续保留 |
| `applicant_id` | 申请人 | `BIGINT UNSIGNED` | 否 | 无 | 外键 → `user.id`，删除限制 | 否 | `(applicant_id, status)` 联合索引 | 不适用 | 当前登录用户 | 学生不能手动指定 |
| `applicant_name_snapshot` | 提交时姓名快照 | `VARCHAR(50)` | 否 | 无 | 否 | 否 | 无 | 不适用 | 从提交时 `user.name` 复制 | 此后不随用户资料变化 |
| `applicant_major_class_snapshot` | 提交时专业班级快照 | `VARCHAR(100)` | 否 | 无 | 否 | 否 | 无 | 不适用 | 从提交时 `user.major_class` 复制 | 不保存手机号快照 |
| `club_id` | 申请社团 | `BIGINT UNSIGNED` | 否 | 无 | 外键 → `club.id`，删除限制 | 否 | `(club_id, status, applied_at)` 联合索引 | 不适用 | 从目标招新所属社团取得 | 必须等于 `recruitment.club_id` |
| `recruitment_id` | 目标招新 | `BIGINT UNSIGNED` | 否 | 无 | 外键 → `recruitment.id`，删除限制 | 否 | `(recruitment_id, applicant_id, status)` 联合索引 | 不适用 | 当前招新上下文 | 学生不能手动修改 |
| `reason` | 申请理由 | `TEXT` | 否 | 无 | 否 | 否 | 无 | 不适用 | 申请人输入 | 申请人唯一手动填写的申请字段 |
| `applied_at` | 申请时间 | `DATETIME` | 否 | 无 | 否 | 否 | 见 `club_id` 联合索引 | 不适用 | 系统生成 | 不增加审核时间 |
| `status` | 申请状态 | `ENUM` | 否 | `待审核` | 否 | 否 | 见各联合索引 | `待审核`、`已通过`、`已拒绝` | 系统设置 | 不增加审核人、审核原因、审核说明或独立审核结果 |

### 6.3 表级约束与并发控制

- `club_id` 必须与 `recruitment_id` 指向招新的 `club_id` 一致，由服务端联合校验。
- 同一申请人、同一招新不得同时存在多条待审核申请。MySQL 普通联合唯一约束无法只约束“待审核”子集，本版不为此增加生成列；应在提交事务中锁定目标招新记录，再按 `(recruitment_id, applicant_id, status)` 查询并校验，避免并发提交产生重复待审核申请。
- 被拒绝的学生只能申请同一社团后续发布的新招新信息；服务端按招新记录及发布时间关系校验，不增加额外字段。
- 通过申请时必须锁定申请、招新及相关成员关系，重新检查容量；申请状态变化、成员关系创建或恢复以及通知生成必须同时成功。
- 不保存成员结果外键；成员结果通过 `(applicant_id, club_id)` 查询唯一成员关系。

## 15. 外键删除策略总表

| `join_application.recruitment_id` | `recruitment` | 限制删除 | 保留申请对应的招新 |
| `announcement.club_id` | `club` | 限制删除 | 注销社团后保留公告历史 |
| `announcement.publisher_id` | `user` | 限制删除 | 保留公告发布人 |
| `post.club_id` | `club` | 限制删除 | 注销社团后保留帖子历史 |
| `post.author_id` | `user` | 限制删除 | 停用用户后保留帖子历史 |
| `reply.post_id` | `post` | 限制删除 | 父帖逻辑删除时回复继续保留 |

| `post_like.post_id` | `post` | 限制删除 | 帖子逻辑删除不级联物理删除点赞关系 |
| `notification.recipient_id` | `user` | 限制删除 | 停用用户后保留历史通知 |
| `club_evaluation.user_id` | `user` | 限制删除 | 停用用户后保留评价历史 |
| `club_evaluation.club_id` | `club` | 限制删除 | 注销社团后保留评价历史 |
| `club_evaluation.membership_id` | `club_membership` | 限制删除 | 退出或移除时保留成员关系和评价 |
| `feedback.submitter_id` | `user` | 限制删除 | 保留反馈提交人 |
| `feedback.club_id` | `club` | 限制删除 | 注销社团后保留反馈历史 |
| `content_report.reporter_id` | `user` | 限制删除 | 保留举报人 |
| `content_report.post_id` | `post` | 限制删除 | 通过逻辑删除后的原帖子查看历史内容 |
| `content_report.reply_id` | `reply` | 限制删除 | 通过逻辑删除后的原回复查看历史内容 |

`post_like` 取消点赞时删除的是点赞关系自身，不是由父记录删除触发的级联删除。

## 16. 持久化状态、动态结果与逻辑删除

### 16.1 持久化字段

| 对象 | 持久化字段 | 允许值或事实 |
|---|---|---|
| 用户 | `user.account_status` | 正常、已停用 |
| 社团 | `club.status` | 正常、已注销 |
| 成员关系 | `club_membership.member_status` | 在社、已退出、已移除 |
| 成员关系 | `club_membership.club_role` | 负责人、普通成员 |
| 招新 | `recruitment.ended_early` | 是否提前结束的事实 |
| 入社申请 | `join_application.status` | 待审核、已通过、已拒绝 |
| 公告 | `announcement.status` | 正常、已删除 |
| 帖子 | `post.status` | 正常、已删除 |
| 回复 | `reply.status` | 正常、已删除 |
| 反馈 | `feedback.status` | 待处理、已处理 |
| 举报 | `content_report.status` | 待处理、已采纳、未采纳 |

### 16.2 动态结果

- 招新“未开始、进行中、已满、已结束”不落库，依据 `ended_early`、服务端当前时间、`start_time`、`end_time`、`capacity` 和已通过申请数量实时计算。
- 招新已通过人数由 `join_application` 中对应招新且状态为“已通过”的记录实时统计，不保存计数字段。
- 用户总数、正常社团数、在社成员数、待审核申请数、当前招新数、正常帖子数、待处理反馈数、待处理举报数和本人当前加入正常社团数均实时查询，不保存统计结果；负责人概览的帖子数只统计 `post.status=正常`。

### 16.3 逻辑删除与物理删除

- `announcement`、`post`、`reply` 使用各自的 `status` 字段逻辑删除。
- 用户停用、社团注销、成员退出或移除均更新需求规定的状态，不物理删除记录。
- 举报继续引用已逻辑删除的原帖子或回复，不保存快照。
- `post_like` 是当前关系，取消点赞时允许物理删除该关系。
- 其他表不增加需求以外的删除、恢复或定期物理清理功能。

## 17. 必须由服务端事务与联合校验保证的约束

| 业务操作 | 必须锁定或核对的数据 | 原子结果 |
|---|---|---|
| 创建社团 | 新社团、初始负责人用户 | 社团与至少一条“在社、负责人”成员关系同时创建成功 |
| 停用学生账号 | 目标用户、其负责的正常社团及有效负责人关系 | 任一社团会失去最后有效负责人时拒绝整次停用 |
| 添加负责人 | 目标用户、目标社团、唯一成员关系 | 仅将账号正常且当前“在社、普通成员”的关系改为负责人 |
| 取消负责人身份 | 目标社团及有效负责人关系 | 操作后仍有有效负责人，再把目标身份改为普通成员 |
| 提交入社申请 | 目标招新、同一申请人相关申请、当前成员关系 | 仅在动态状态为进行中、申请人不在社且无重复待审核申请时创建 |
| 通过入社申请 | 申请、招新、已通过申请集合、唯一成员关系 | 容量未满时，申请变为已通过，成员关系创建或恢复为“在社、普通成员”，并生成通知 |
| 拒绝入社申请 | 申请 | 申请变为已拒绝并生成通知，不改变成员关系 |
| 发布回复 | 父帖子、作者成员关系 | 回复创建为正常并生成帖子回复通知 |
| 提交评价 | 用户、社团、成员关系、已有评价 | 三者一致且当前有效；同一成员关系只创建或更新一条评价 |
| 提交反馈 | 用户、社团、成员关系 | 当前有效成员才能创建待处理反馈 |
| 处理反馈 | 反馈、负责人成员关系 | 保存可选处理说明并把状态改为已处理；未填写时允许为空 |
| 提交举报 | 举报人权限、目标帖子或回复 | 只保存一个有效目标，目标社团从内容关系确定 |
| 处理举报 | 举报、负责人成员关系、可选的目标内容 | 保存必填处理说明、更新举报状态并生成通知；是否删除内容按独立操作规则处理 |

## 18. 隐私与快照边界

| 数据 | 存储位置 | 逻辑设计要求 |
|---|---|---|
| 用户当前手机号 | `user.phone` | 学生本人和系统管理员可查看；负责人只在本人负责社团的当前在社成员管理中查看 |
| 申请姓名快照 | `join_application.applicant_name_snapshot` | 提交时从 `user.name` 复制，之后不随资料变化 |
| 申请专业班级快照 | `join_application.applicant_major_class_snapshot` | 提交时从 `user.major_class` 复制，之后不随资料变化 |
| 申请手机号快照 | 不存储 | 负责人查看申请时不展示手机号 |
| 举报内容快照 | 不存储 | 通过原帖子或回复及其逻辑删除状态保留历史 |
| AI 问题、上下文、回答和文档草稿 | 不存储 | 仅在单次请求中使用，不新增任何表或字段 |

## 19. 已确认约束与第一版边界

### 19.1 社团名称唯一性

用户于 2026-07-28 确认社团名称唯一。`club.name` 建立唯一约束，创建和修改接口必须处理重名错误。

### 19.2 帖子与回复最大长度

用户于 2026-07-28 确认帖子标题最多 255 字、帖子正文最多 5000 字、回复内容最多 1000 字。存储类型保持不变，服务端和页面按相同字符上限校验。

### 19.3 可选图片能力

公告图片和帖子图片属于时间允许再完善的功能。当前不增加图片字段、图片表、附件表、上传关系、数量限制或大小限制。
