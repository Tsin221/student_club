# S15：内容举报 — 实现说明

## 文档信息

- **切片 ID**：S15
- **用户结果**：当前在社成员举报可见帖子或回复；负责人处理本人负责社团举报，举报人收到结果通知
- **依赖**：S11
- **状态**：已验收

## 实现范围

### 新增模型

| 模型 | 表名 | 说明 |
|---|---|---|
| `ContentReport` | `content_report` | 内容举报：关联举报人、被举报的帖子或回复（XOR）、举报原因、处理状态、处理说明 |

**字段设计：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BigAutoField` | 主键 |
| `reporter` | `FK → User` | 举报人，`PROTECT`，`db_column="reporter_id"` |
| `reason` | `TextField` | 举报原因（必填） |
| `post` | `FK → Post` | 被举报帖子，`null=True`，`PROTECT`，`db_column="post_id"` |
| `reply` | `FK → Reply` | 被举报回复，`null=True`，`PROTECT`，`db_column="reply_id"` |
| `status` | `CharField(max_length=20, choices)` | `待处理` / `已采纳` / `未采纳`，默认 `待处理` |
| `processing_note` | `TextField(null=True, blank=True)` | 处理说明（待处理时可为 null，处理时必填） |

**约束与索引：**

- `(post_id, status)` 复合索引（`cr_post_status_idx`）
- `(reply_id, status)` 复合索引（`cr_reply_status_idx`）
- **XOR 约束**：`post_id` 和 `reply_id` 必须且只能有一个非 null，在服务层强制
- 不存储 `club_id`，社团归属通过目标内容的 `post.club_id` 或 `reply.post.club_id` 推导
- 不保存内容快照，target 信息从原帖/回复实时读取
- 不保存处理人、处理时间（按阶段一设计）
- FK 均使用 `RESTRICT` 策略，原内容逻辑删除后仍可追溯
- 管理员完全无权访问举报接口

| `Notification` | 处理举报后向举报人生成 `REPORT_PROCESSED` 类型通知（该类型 S07 已预设） |

## 关键实现决策

### 1. XOR 约束在服务层强制

`ContentReport.post` 和 `ContentReport.reply` 均为可空 FK，提交时通过不同的 URL 端点（`/api/posts/{post_id}/reports` 和 `/api/replies/{reply_id}/reports`）确保每次只有一侧赋值。不在数据库层加 CHECK，与项目现有 `PostLike` 等模式保持一致，避免 MySQL 版本兼容问题。

### 2. 社团归属推导而不存储 `club_id`

举报不单独存储 `club_id` 字段。需要社团归属时，通过 `report.post.club_id`（举报帖子）或 `report.reply.post.club_id`（举报回复）实时推导。列表查询使用 Django ORM 的 Q 对象过滤：

```python
Q(post__club_id=club_id) | Q(reply__post__club_id=club_id)
```

这样避免了冗余字段和潜在的数据不一致。

### 3. 处理为事务性操作

`leader_process_report` 使用 `transaction.atomic()` 确保以下步骤原子执行：
1. 更新 `report.status` 和 `report.processing_note`
2. 若 `delete_target=true`：将目标帖/回复的 `status` 设为 `已删除`
3. 创建 `Notification(type=REPORT_PROCESSED, …)`

任何一步失败则全部回滚。

### 4. 已删除目标仍可处理

按阶段一设计，不保存内容快照。当被举报的帖子或回复已通过其他途径（如作者本人删除、S16 管理员删除等）逻辑删除后，负责人仍可对该举报执行处理（`delete_target=true` 时跳过已删除目标的重复操作），通知照常生成。

### 5. 采纳不等于自动删除

`status=已采纳` 且 `delete_target=false` 时，仅更新举报结论，不对目标内容做任何修改。`delete_target` 是处理时的操作参数，不持久化到举报记录中。

### 6. 处理说明必填

`status=未采纳` 时也必须填写 `processing_note`，解释不予采纳的理由。空白字符串或缺失均返回 `PROCESSING_NOTE_REQUIRED`（400）。这与反馈（`processing_note` 可选）不同。

### 7. target 按需返回

序列化函数 `serialize_content_report(report, include_target=False)` 通过可选参数控制是否附加被举报内容的实时信息。负责人列表使用 `include_target=True`，返回 posting/reply 的完整摘要（含标题/内容、状态、作者），用于展示举报上下文。

### 8. 复用已有通知类型

`Notification.Type.REPORT_PROCESSED`（"我的举报已经处理"）在 S07 已预设但一直无生产者。S15 是首个使用该类型的切片，`StudentNotificationsView.vue` 的颜色映射（橙色）也已有预设，无需改动前端通知页。

### 9. 举报入口嵌入现有帖子流

由于项目当前没有独立帖子详情页，举报按钮直接放在 `StudentClubDetailView` 的每个帖子卡片（点赞旁）和每条回复的右侧。这与 S12 点赞、S11 回复的嵌入方式一致。

## 错误码

| 错误码 | HTTP 状态 | 场景 |
|---|---|---|
| `INVALID_REQUEST` | 400 | `reason` 缺失/空白/非字符串，或提交不允许的字段 |
| `POST_DELETED` | 400 | 帖子已删除（无法举报） |
| `REPLY_DELETED` | 400 | 回复已删除（无法举报） |
| `NOT_CLUB_MEMBER` | 403 | 非社团成员举报 |
| `MEMBERSHIP_INACTIVE` | 403 | 已退出或已移除的成员举报 |
| `CLUB_CANCELLED` | 409 | 社团已注销 |
| `NOT_CLUB_LEADER` | 403 | 非负责人查看或处理举报 |
| `REPORT_ALREADY_PROCESSED` | 409 | 重复处理已处理的举报 |
| `INVALID_REPORT_STATUS` | 400 | 处理结论不是 `已采纳` 或 `未采纳` |
| `PROCESSING_NOTE_REQUIRED` | 400 | 处理说明缺失或空白 |
| `INVALID_DELETE_DECISION` | 400 | 未采纳时请求删除目标内容 |
| `RESOURCE_NOT_FOUND` | 404 | 帖子/回复/举报 ID 不存在 |
