## 2. S00 的目标

S00 用于建立后续业务切片共同依赖的开发基础，使开发者可以：

1. 使用 Docker Compose 启动本地 MySQL 8。
2. 启动 Django 后端并连接 MySQL。
3. 启动 Vue 3 前端并使用 Element Plus。
4. 在首次数据库迁移前启用自定义用户模型。
5. 运行后端检查、数据库迁移、自动测试、前端类型检查和构建。
6. 通过统一配置管理本地秘密，不把真实密码或密钥写入源码。

S00 只建立工程基础，不实现注册、登录、社团管理或其他业务功能。

### 3.4 自定义用户模型

当前用户表只包含阶段一设计所要求的平台账号和个人资料字段：

| 字段 | 说明 |
|---|---|
| `id` | 用户主键 |
| `username` | 唯一用户名 |
| `password_hash` | Django 密码哈希，模型字段名为 `password` |
| `platform_role` | 平台角色：系统管理员或学生 |
| `account_status` | 账号状态：正常或停用 |

社团负责人、普通成员等社团内身份没有写入用户表，后续由社团成员关系表达，避免把平台角色和社团角色混为一体。

### 3.5 统一 API 响应基础

后端在 `core` 应用中建立了统一响应和异常处理基础。

成功响应结构：

```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {}
}
```

错误响应结构：

```json
{
  "code": "ERROR_CODE",
  "message": "可安全展示的错误信息",
  "data": null
}
```

当前已实现：

- 统一成功响应函数。
- 统一错误响应函数。
- 可携带业务错误码和 HTTP 状态码的 `ApiError`。
- 未预期异常统一转换为 `INTERNAL_ERROR`，不向客户端返回内部异常内容。

S00 没有新增业务 API；这些基础能力将在后续切片中复用。

## 5. 启动方式

### 5.1 启动 MySQL

在 `code` 目录运行：

```powershell
docker compose up -d
docker compose ps
```

### 5.2 启动 Django

在 `code/backend` 目录运行：

```powershell
uv sync --locked
uv run python manage.py migrate
uv run python manage.py runserver 127.0.0.1:8000
```

### 5.3 启动 Vue

另开终端，在 `code/frontend` 目录运行：

```powershell
npm ci
npm run dev
```

浏览器访问 `http://127.0.0.1:5173`。

## 7. 关键决定及原因

### 7.1 MySQL 只允许从当前电脑访问

端口映射固定为 `127.0.0.1:3306:3306`，满足本地 Django 和数据库管理工具连接需要，同时避免数据库端口暴露给其他电脑。

### 7.2 首次迁移前建立自定义用户模型

Django 项目后期再替换用户模型会显著增加迁移复杂度，因此 S00 在任何业务表产生之前完成自定义用户模型和 `AUTH_USER_MODEL` 配置。

### 7.3 平台角色与社团身份分离

用户表只保存系统管理员和学生两种平台角色。社团负责人、成员等身份依赖具体社团，后续应保存在社团成员关系中。

### 7.4 真实秘密只放在本地 `.env`

Compose 和 Django 只引用环境变量，不在配置文件中写死密码。`.env.example` 只提供变量名称和占位值。

### 7.5 保持 S00 最小范围

当前没有注册、登录、业务 API、业务数据库表或正式业务页面。这样可以先验证工程基础，再从 S01 开始按垂直切片逐步加入业务能力。

## 8. 已知限制

1. Element Plus 当前采用全量引入，生产构建会提示 JavaScript 包体积超过 500 kB；不阻塞 S00，后续可按需改为自动按需导入。
2. 本地开发密码和 Django 密钥强度不适合部署环境；部署前必须更换为独立生成的强随机秘密。
3. Compose 当前没有 healthcheck 和自动重启策略，这是本地简化配置，不代表生产部署方案。
4. 本地 Git 仓库以 `s00` 作为 S00 的首次提交，当前尚未配置远程仓库。
