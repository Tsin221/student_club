## 2. S01 的目标

S01 建立第一条真实业务垂直路径，使未登录学生可以：

1. 在 `/register` 填写完整资料并创建学生账号。
2. 注册成功后返回 `/login`，且注册过程不自动创建登录会话。
3. 使用用户名和密码登录，由 Django 创建服务端 Session。
4. 进入 `/student` 查看本人账号和资料。
5. 刷新 `/student` 后，继续通过 `HttpOnly` Session Cookie 从服务端取得本人资料。

本切片只涉及 `user` 实体和四个既定接口，不增加登出、找回密码、验证码、第三方登录、头像、资料修改或其他业务能力。

## 3. 已完成的内容

### 3.1 后端认证与资料接口

已实现以下接口：

| 方法与路径 | 用途 | 关键行为 |
|---|---|---|
| `GET /api/auth/csrf` | 初始化 CSRF | 返回 `csrf_token` 并设置 CSRF Cookie |
| `POST /api/auth/register` | 注册学生 | 只接受六个既定字段；固定创建“学生用户、正常状态”账号；成功返回 `201`，不登录 |
| `POST /api/auth/login` | 用户名密码登录 | 校验凭据和账号状态；成功创建 Django Session |
| `GET /api/me/profile` | 读取本人资料 | 从服务端会话取得当前学生，重新校验账号状态和平台角色 |

所有接口继续使用 S00 建立的统一响应包装：

```json
{
  "code": "SUCCESS",
  "message": "操作结果",
  "data": {}
}
```

失败响应保持 `data=null`，并使用稳定错误码。

### 3.2 注册边界与密码安全

注册请求只允许：

- `username`
- `password`
- `name`
- `phone`
- `major_class`
- `grade`

请求缺字段、增加字段、字段类型错误或空值时返回 `INVALID_REQUEST`。客户端提交 `platform_role`、`account_status`、`registered_at` 等系统字段会被拒绝。

密码处理遵循以下规则：

- 使用 Django 默认密码校验器检查长度、常见密码、纯数字密码和用户属性相似度。
- 使用 `set_password()` 生成安全哈希，数据库不保存明文。
- API 的 `SelfUser` 投影不包含密码或密码哈希。
- 用户名不存在和密码错误均返回 `INVALID_CREDENTIALS`；不存在用户同样执行一次密码哈希运算，降低凭据校验的时间差异。
- 用户名重复返回 `USERNAME_EXISTS`；数据库唯一约束异常也映射为同一错误码。

### 3.3 Session、账号状态与权限

- 登录成功通过 Django `login()` 创建服务端 Session。
- Session Cookie 继承 S00 配置：`HttpOnly`、`SameSite=Lax`，非调试环境启用 `Secure`。
- 前端不在 `localStorage`、`sessionStorage` 或普通 Cookie 保存 Bearer Token。
- 新增 `SessionUserBackend`，使账号在已有会话期间被停用后，后端仍能识别该用户并在受保护接口返回 `ACCOUNT_DISABLED`。
- `/api/me/profile` 只允许账号正常的学生访问；未登录返回 `UNAUTHENTICATED`，非学生返回 `FORBIDDEN`。

### 3.4 CSRF

- 注册和登录提交前，前端调用 `GET /api/auth/csrf`。
- 写请求通过 `X-CSRFToken` 请求头提交令牌。
- Django CSRF 中间件负责校验；缺少或错误令牌统一返回 `CSRF_FAILED`。
- CSRF 令牌只用于请求防护，不作为认证令牌或业务字段。

### 3.5 前端请求层

`src/api/auth.ts` 提供注册、登录、本人资料和 CSRF 请求能力：

- 每次认证写请求先初始化 CSRF。
- 所有请求使用 `credentials: same-origin`。
- 统一解包 `code`、`message`、`data`。
- 非成功响应转换为带稳定 `code` 的 `ApiRequestError`。
- 对成功响应中的本人资料再次执行运行时结构检查，避免页面直接使用不完整或异常响应。
- 注册请求显式挑选六个允许字段，不转发额外属性。

### 3.6 页面与路由

已实现：

| 路由 | 页面结果 |
|---|---|
| `/register` | 完整注册表单；失败保留输入；成功跳转登录页并显示成功提示 |
| `/login` | 用户名密码登录；显示错误凭据、停用账号、CSRF 等接口提示 |
| `/student` | 最小个人中心；展示默认头像、账号状态、用户名、姓名、手机号、专业班级、年级和注册时间 |

页面采用阶段一确认的白色与蓝色视觉体系，使用 Element Plus 表单、提示、标签、加载状态和资料描述组件。表单支持键盘操作、浏览器自动填充属性和明确标签；个人中心加载失败时提供重新加载入口。

登录页和注册页使用本人资料接口探测已存在的学生会话，已登录学生会回到 `/student`。未登录直接进入 `/student` 时，资料接口返回 `UNAUTHENTICATED`，页面跳回 `/login?reason=session`。

## 8. 关键决定及原因

### 8.1 注册成功不建立会话

严格遵循切片边界：注册只创建账号，前端跳转登录页。这样注册与认证是两个可独立验证的动作。

### 8.2 服务端固定系统字段

平台角色、账号状态和注册时间不从请求体读取。即使绕过前端直接调用接口，也不能注册管理员、创建停用账号或伪造注册时间。

### 8.3 已有会话仍重新检查停用状态

默认 Django 认证后端会把停用用户会话直接解释为匿名用户。S01 使用专用会话后端保留用户识别，再由受保护接口显式返回 `ACCOUNT_DISABLED`，满足“停用后已有会话也必须被拒绝”的设计。

### 8.4 不增加前端认证令牌

前端只依赖浏览器自动携带的 `HttpOnly` Session Cookie。CSRF 令牌不是登录凭据，不写入本地持久化认证状态。

### 8.5 不增加需求外接口

没有增加通用会话接口、登出、修改密码或管理员页面。路由守卫通过既有本人资料接口执行，保持 S01 接口范围不变。

## 9. 已知限制

1. Element Plus 仍按 S00 方式全量引入，生产构建存在大于 500 kB 的包体积警告；不阻塞 S01。
2. 阶段一没有定义登录限流策略、阈值或对应错误码，S01 未自行发明限流业务规则；对公网部署前应先确认契约再增加持久化或共享式认证限流。
3. 未登录状态探测本人资料时，浏览器开发工具会记录预期的 `401` 网络响应；页面会按错误码正常回到登录状态，不属于应用脚本异常。
4. 本切片按设计不提供登出、找回密码、验证码、第三方登录、头像或资料修改入口。
